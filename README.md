# Is CrossQ robust to a weakening body?

Code, configurations, raw results and analysis for a BIOE70077 (Imperial College London)
reinforcement-learning coursework paper by Emily Gan.

**Question.** Does a change in muscle force capacity during training, gradual or sudden, harm
CrossQ, a batch-normalised off-policy actor-critic, more than a constant loss of the same size?

**Setting.** MyoSuite Hand Reach (39 muscles, 5 fingertip targets), 500k training steps. Every
muscle's fatigued fraction is set by a schedule over training: No fatigue (0), Fixed (0.5 from the
start), Drift (0 to 0.5 over 400k steps) or Sudden (0 to 0.5 at 250k). SAC is the baseline.

**Main results** (CrossQ, mean return over the final 100k steps, seed-paired, 95% bootstrap CI):

| Comparison | Seeds | Difference | Verdict |
|---|---|---|---|
| Cost of fatigue (No fatigue - Fixed) | 8 | 119.3 [46.7, 203.0] | fatigue lowers return |
| H1, drift penalty (Fixed - Drift) | 8 | -32.9 [-103.9, 28.5] | inconclusive, t-interval excludes penalties above 54 |
| H4, sudden penalty (Fixed - Sudden, 255k-350k) | 5 | 31.7 [-7.6, 65.0] | inconclusive, t-interval excludes penalties above 89 |

SAC and two CrossQ variants without batch normalisation did not learn the task, so the role of
batch normalisation could not be isolated. Full results: `tables/hypotheses.md`,
`tables/main_results.md`. The paper is submitted separately.

## Environment

All GPU runs used Kaggle sessions with 2x NVIDIA T4, Python 3.11.5, JAX 0.4.19 (CUDA 12).
There are two environments, and every run folder records its own exact package list
(`packages.txt`):

| Environment | Used for | Key versions | File |
|---|---|---|---|
| `env-baseline` | Walker2d reproduction | authors' pins: MuJoCo 2.3.7, gymnasium 0.29.1, torch 2.1.2, plus cuDNN 8.9.7.29 | `environment/requirements-reproduction.txt` |
| `env-dev` | all MyoSuite runs and the bridge runs | MyoSuite 2.8.4, MuJoCo 3.1.2, gymnasium 0.29.1, torch 2.0.1 | `environment/requirements-myosuite.txt` |

The core packages (JAX, jaxlib, MuJoCo, MyoSuite, torch, gymnasium, Flax, Optax,
Stable-Baselines3, NumPy, cuDNN, cuSOLVER) are identical in every run of each environment. A few
unpinned utility packages (for example cmake, filelock) differ by a patch version between Kaggle
sessions.

To rebuild `env-dev` and the patched CrossQ code on Kaggle (Internet on, GPU T4 x2):

```bash
cd /kaggle/working && bash kit/environment/setup_kaggle.sh   # after cloning this repo as kit/
```

`HOW_TO_RUN.md` describes the reproduction environment and the setup in more detail.

## Reproducing the experiments

One run: `scripts/run_experiment.sh <config> <seed> <gpu>`. Several runs spread over the GPUs:
`PER_GPU=1 scripts/run_batch.sh <config>:<seed> ...`. Each run writes a folder to `results/raw/`
and a row to `results/run_log.md`.

| Experiment | Configs | Seeds | Runs | GPU-hours |
|---|---|---|---|---|
| Walker2d reproduction | `configs/repro/walker2d_{crossq,sac}.cfg` | 1-5 | 10 | 16.9 |
| Hand Reach design pilot | `configs/pilot/handreach_{crossq,sac}_{nofatigue,drift}.cfg` | 1 | 4 | 8.8 |
| Main, CrossQ | `configs/main/handreach_crossq_{nofatigue,fixed,drift}.cfg` | 11-18 | 24 | 55.2 |
| Main, CrossQ Sudden | `configs/main/handreach_crossq_sudden.cfg` | 11-15 | 5 | 12.5 |
| Main, SAC | `configs/main/handreach_sac_{nofatigue,fixed,drift}.cfg` | 11-15 | 15 | 21.1 |
| Variants without Batch Renormalization (pilots) | `configs/pilot/handreach_crossqln_nofatigue.cfg`, `handreach_crossqnobn_nofatigue.cfg` | 1 | 2 | 4.3 |
| Bridge (Walker2d in the MyoSuite setup) | `configs/bridge/walker2d_{crossq,sac}.cfg` | 1 | 2 | 2.7 |
| Amendment 4 sweep | `configs/sweep/handreach_crossq_{nofatigue,fixed}_sweep.cfg` | 11-13 | 6 | 13.7 |

Total: 68 runs, 135.1 GPU-hours (per-group times in `tables/settings_compute.md`). A CrossQ Hand
Reach run takes about 135-170 min on one T4, a SAC run about 80-95 min.

## Reproducing the figures and tables

Every figure and table is generated from `results/raw/` by a script. Run from the repository root
with the MyoSuite environment's Python (numpy, scipy and matplotlib are enough for the analysis):

```bash
python scripts/analyze_repro.py results           # Fig. 2, reproduction tables
python scripts/analyze_main.py results            # Figs. 3-6, Tables III-V, sudden-drop windows
python scripts/analyze_h1.py results              # H1 with minimum detectable effect
python scripts/analyze_ramp.py results            # secondary measure (dip during the ramp)
python scripts/analyze_bridge.py results          # bridge runs vs reproduction
python scripts/analyze_sudden_windows.py results  # paired CIs around the sudden drop
python scripts/analyze_variation.py results       # run-to-run variation of identical runs
python scripts/analyze_sweep.py results           # Amendment 4 sweep tables
CODE_DIR=/path/to/CrossQ-dev python scripts/analyze_activation.py results   # Fig. 7, muscle use of the saved policies (CPU, ~6 min)
python scripts/make_method_figure.py              # Fig. 1 (Graphviz + matplotlib; needs dot and rsvg-convert)
PYTHONPATH=src python tests/test_fatigue_drift.py # unit tests of the fatigue schedule (MyoSuite env)
python scripts/check_builtin_fatigue.py results/builtin_fatigue.csv   # MyoSuite env
python scripts/check_activation_saturation.py     # MyoSuite env
```

## Pre-registration

`HYPOTHESIS.md` was committed before any main run (7 Nov 2026) and fixes the hypotheses, the
primary metric (mean evaluation return over 400k-500k), the analysis (seed-paired differences,
95% bootstrap CI) and decision rules. Four dated amendments, each committed before the runs it
governs, record every change, and the batch table there lists the status of every planned batch.
The git history shows the order of amendments and results.

## Run records

Each folder in `results/raw/` holds the config used, `meta.txt` (command, code commit, GPU,
start and end time, exit code), `code.diff` (the applied patch), `packages.txt`, the full training
log and `evaluations.npz` (10 evaluation episodes every 5,000 steps, return and success). The
Amendment 4 runs also hold `fatigue_sweep.npz` and the trained actor (`final_actor.pkl`).

Every run executed is accounted for: the 68 runs in `results/raw/`, the three elbow-task pilots in
`results/pilot_elbow/`, and the 7 runs of a first Batch 4 attempt that crashed at start-up without a
GPU and were rerun unchanged (recorded in `HYPOTHESIS.md` and `notes/run_notes.md`).
`notes/run_notes.md` also lists what did not work and which Kaggle notebook ran each batch.

## Use of AI

This project used Claude (Anthropic), through claude.ai, as an assistant
([[model and version]]). The author chose the topic and research question, made the design
decisions (including the pre-registration and every amendment), ran every experiment on Kaggle,
and checked and approved all changes. The assistant helped to:

- plan the experiments and draft `HYPOTHESIS.md` and its amendments for the author to approve
- write and test code: the fatigue wrapper, the patch, configs, run and analysis scripts, tests
- analyse the raw results with scripts and draft figures and tables
- check literature and citations, and draft and edit text of the paper and these documents

The assistant worked in its own workspace and committed to this repository on the author's
behalf, so most commits show "Claude" as the git author and end with a `Claude-Session` line. Seven
early commits also carried a `Co-Authored-By` line. That line was dropped because an AI is not an
author of this work. The assistant also ran short CPU checks of the code, which are not results
(see `notes/run_notes.md`). One design flaw came from the assistant's setup of the LayerNorm pilot
(see `notes/run_notes.md`). Every reported number is computed by the scripts above from the raw
Kaggle runs.
